What the team diagnosis gets right
The duplicate INVITE / two ElevenLabs sessions and immediate 200 OK before callee answers are both confirmed binary bugs. The log is unambiguous:

Same Call-ID processed twice, no guard → two independent ElevenLabs connections spin up
Binary auto-answers at 17:49:54.615, ElevenLabs audio starts flowing at 17:49:56 — but the first RTP packet from the callee doesn't arrive until 17:49:57.124. The AI is talking into silence before the person even picked up.
These cannot be fixed server-side. The outboundContext.ts and outbound.ts files only feed the binary config — they have no influence on how the binary handles SIP signaling.

The extension restart after the call — this is intentional
The "extension reconnects" you're seeing is the orphan cleanup in deployment.ts working exactly as designed (lines 261–296). Here's what happens:

The binary processes both INVITEs → two ElevenLabs WebSocket sessions open
BYE arrives → the binary closes session 1 and sends Unregistered bridge
Our server detects "bridge unregistered for a call that already ended" → schedules a 5-second restart
Restart kills the process → kills the orphaned session 2 WebSocket → extension re-registers
The restart is the only server-side lever we have to kill the zombie second session. Without it, session 2 would stay open consuming ElevenLabs minutes indefinitely. It's not a bug, it's the workaround for the binary's duplicate-bridge problem.

The real hidden issue: outbound overrides not being applied
This is what jumped out at me from the log. You set Hakim (outbound persona) in the trigger form. The binary used Hamza (inbound config) instead:

Overriding first_message: Bonjour, vous êtes bien chez AIO PROCESS. Je suis Hamza...
Sending conversation initiation: {...first_message: "Bonjour...Hamza..."}

ElevenLabs confirms it — both conversations show the inbound Hamza substitutions.

I traced the entire server-side chain:

The context is stored before the Yeastar dial call (correct ordering) ✓
The key used is the DB integer ID in both setPendingContext and the context_webhook_url ✓
consumePendingContext is non-consuming (it was deliberately changed to not delete on read) ✓
clearPendingContext is never called prematurely — the only callers are the TTL timer and nowhere else ✓
So our side is correct. The binary getting pending: false (which causes it to fall back to config-file values) means either:

A) The binary calls the context webhook at registration time (startup), not per-call. If that's the case, the context doesn't exist yet when it's called, so it gets pending: false, caches that result, and uses config values for all calls until the next restart. This would explain why inbound overrides work (they're baked into the config file) but outbound overrides don't (they're only set at call trigger time).

B) There was a server restart between trigger and INVITE arrival — in-memory context wiped.

Scenario A is the more likely culprit structurally, and it would also explain why restarting the extension after setting up a new outbound call might accidentally make it work (the restart forces a fresh context fetch).
