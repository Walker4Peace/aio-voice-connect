Bug : les appels outbound ne raccrochent jamais côté serveur (bridge RTP/ElevenLabs reste ouvert), et l'appel se coupe automatiquement après ~34s si personne ne raccroche avant.

Root cause confirmée par analyse pcap (Wireshark) :

Sur le leg SIP local entre notre client SIP (sipgo) et le proxy outbound, quand l'appel outbound est décroché, le proxy envoie le 200 OK final de l'INVITE :

t=14.559s  proxy -> app   SIP/2.0 200 OK   (CSeq: 2 INVITE)

Notre client SIP n'envoie JAMAIS l'ACK pour ce 200 OK. Preuve : dans tout le pcap, le seul ACK sortant de notre app (4070 -> 5060) est envoyé à t=5.062s pour le 401 Unauthorized (challenge d'auth) — ça, ça marche car sipgo le gère automatiquement au niveau de la transaction. Mais pour le 200 OK de succès, il n'y a AUCUN ACK envoyé.

Résultat : le proxy retransmet le 200 OK indéfiniment (0.5s, 1s, 2s, 4s, 4s, 4s… — pattern classique RFC 3261 de retransmission faute d'ACK), jusqu'à ce que la transaction expire côté PBX (~32s après le premier 200 OK), ce qui explique la coupure automatique vers 34s.

Et comme le dialog SIP n'est jamais marqué "confirmed" en interne (faute d'ACK envoyé), notre code ne reconnaît pas correctement le BYE envoyé par le correspondant quand il raccroche — donc le handler qui doit fermer le bridge RTP ↔ ElevenLabs ne se déclenche jamais, et le bridge reste ouvert même après que l'appel soit terminé côté téléphone.

Pourquoi ça n'arrive qu'en outbound et pas en inbound :
En SIP, l'ACK sur une réponse 2xx à un INVITE doit être construit et envoyé manuellement par le code applicatif (UAC), ce n'est PAS automatique dans sipgo (contrairement à l'ACK sur les erreurs 4xx qui lui est auto-généré par la couche transaction). En inbound, notre app est UAS (on répond avec le 200 OK), donc c'est le PBX qui nous envoie l'ACK — ce chemin fonctionne. En outbound, notre app est UAC et reçoit le 200 OK — c'est justement ce chemin qui manque dans notre implémentation.

Fix demandé :

Trouver l'endroit dans le code où on gère la réponse à l'INVITE sortant (probablement dans le callback OnResponse du client transaction sipgo, juste après les logs "Received 200 OK" / "Call answered!").
Ajouter la construction explicite d'une requête ACK dès qu'on reçoit un 200 OK sur une INVITE :
Même Request-URI que l'INVITE original (ou le Contact reçu dans le 200 OK / Record-Route si présent)
Header To avec le tag reçu dans le 200 OK
Même Call-ID, même From avec son tag
CSeq avec le même numéro que l'INVITE mais méthode ACK
Envoyer cet ACK dans une transaction séparée, pas via la transaction client de l'INVITE (l'ACK sur 2xx est hors-transaction selon RFC 3261 §17.1.1.3, contrairement à l'ACK sur erreur qui est dans la même transaction)
Vérifier ensuite que le handler de BYE entrant se déclenche correctement une fois l'ACK envoyé, et qu'il ferme bien le bridge RTP ↔ ElevenLabs (arrêt propre des goroutines outbound ElevenLabs to RTP bridge / outbound RTP to ElevenLabs bridge, fermeture du listener RTP, fermeture de la connexion websocket ElevenLabs).
Tester : lancer un appel outbound, laisser sonner/décrocher, vérifier dans les logs qu'un ACK sent (ou équivalent) apparaît juste après Call answered!, PUIS raccrocher depuis le téléphone après 15s et vérifier que le bridge se ferme bien dans les logs.
